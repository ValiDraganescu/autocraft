# The game layer in Unreal

This is the plan for `unreal/Source/Autocraft`, the Unreal counterpart of the
Swift app layer `Sources/Autocraft` (about 105 files, 36k lines). The
simulation (`Sources/GameCore` → `Source/AutocraftCore`, namespace `ac`) and
the model export (`Sources/Autocraft/ExportModels.swift` → USDA plus
`manifest.json`) are other agents' work. Read `PORTING.md` first: this file
assumes its layout and rules.

Paths with no directory are in `Sources/Autocraft/`. `file:line` points to
where the code stood on 2026-10-04. Other sessions are editing those files,
so search for the function name if a line has moved.

## 0. What kind of game this is

Autocraft is not a classic RTS front end, and the port must not grow one by
accident. The app layer has **no** unit selection, box select, control
groups, right-click orders, rally clicks, edge scroll or camera rotation. The
human is always player 0 (blue) and plays in three ways:

1. **Buildings and their command card.** The player clicks one of their own
   buildings and presses its buttons. A press the AI could carry out is
   queued for the team's AI commander instead of being refused (co-op).
2. **The command map (M).** The player gives the team's AI orders: a
   stance, objectives (attack, defend, hold, man a Bastion), expansions and
   requests.
3. **Driving one unit**, in first or third person, as a shooter (`Pilot`).

Everything else is the AI: one `ac::Commander` per player.

## 1. Conventions every chunk shares

- **Units and axes.** The sim's `Vec2(x, y)` is SceneKit's world `(x, z)`,
  Y up, right-handed, with 1 world unit = 1 cell. In Unreal (Z up,
  left-handed, cm), use `FVector(x·S, y·S, height·S)` with `S = 100` (a
  cell is 1 m). Mapping SceneKit `(x, y, z)` → UE `(x, z, y)` swaps two axes,
  which also fixes the handedness. Keep this in one header,
  `AcSpace.h` (`ToWorld(Vec2, h)`, `ToSim(FVector)`, `YawFromHeading`).
- **Facing.** Units face +X and SceneKit sets `eulerAngles.y = -heading`.
  Buildings face +Z (UE +Y). After the axis swap a unit's UE yaw should be
  `+heading` in degrees. Check it once with an asymmetric unit (the Longbow's
  horn) against `autocraft preview`, then never touch it again.
- **Exports** (`ExportModels.swift`, the `export-models` command): one
  `.usda` per model (`upAxis = "Y"`, `metersPerUnit = 1`), each part an Xform
  at its rest transform with its rigid children merged per material. Blue and
  red are exported separately. `manifest.json` lists each part's *driver*:
  the channels (rotation, position, visibility, emission, material), the
  Swift functions that move it and their source lines. **That manifest is
  the to-do list for every animation chunk below.** Shader modifiers (opal,
  mercury, terrain, glow) are only notes in it and must be rebuilt as
  materials. `unreal/Tools/README.md`, which the exporter's header names,
  does not exist yet: the export agent owns it.
- **No Blueprint logic.** Gameplay, rendering sync, HUD and audio are in
  C++. Assets that cannot be text (materials, Niagara systems, input
  actions, sound classes) are **made by Python editor scripts in
  `unreal/Tools/Editor/`** (PythonScriptPlugin and EditorScriptingUtilities
  are already enabled), so an agent can read and rerun how each was made.
  C++ looks assets up by path through a single `UAcAssets` table
  (`DeveloperSettings` or one `UDataAsset` made by script).
- **Game time vs. frame time.** The sim steps at 60 Hz with dt clamped to
  0.1 (`AppDelegate.swift:60`, `GameController.tick` at
  `GameController.swift:300-490`). The renderer reads `state.time` for every
  animation. Animations are functions of sim state plus a little
  renderer-only memory per id (`lastShot`, `lastHeading`, `turnRate`, `airY`,
  `cargoCount`, `bornAt`, `flameLength`, `anchorOf`, `forks`, `tankHeading`,
  `lastAim`; `GameScene.forget` :1149). Port that memory as a
  `TMap<int64, FAcUnitMemory>`, not as actor state.
- **Fog gate.** Events the team cannot see (enemy shots, deaths, deposits)
  are dropped *before* they reach the visuals or the sound
  (`GameController.swift:318-335`, `sim.sees`). The renderer draws
  `sim.shown(to: team)` (`Vision.swift:340`): enemy units in sight, plus
  enemy buildings as last seen.

## 3. Architecture of `unreal/Source/Autocraft`

### 3.1 Threads and data flow

```
Game thread, every frame:
  UAcSimSubsystem::Tick(dt)
    accumulate; while (acc >= 1/60): events += sim.step(1/60)   // dt clamp 0.1
    steer pilot (input already folded in), autosave timer
    FAcFrame { const GameState& state; GameState shown; events (fog-gated); time }
  → UAcWorldRenderer::Sync(frame)      // instances, poses, lamps
  → UAcEffects::Consume(frame)         // events → effects, then Update(time)
  → UAcAudioDirector::Consume(frame)   // events → sounds, loops from state
  → AAcHUD / Slate widgets ::Update(frame)
```

- The sim runs on the game thread at first, as in Swift, where it takes a few
  ms. If eight AIs make it too slow, move `step` to a task with a
  double-buffered `GameState` (the copy constructor exists). The renderer
  reads only the front buffer. Do not design for that up front. Measure first
  (§5, chunk P1).
- Nothing in the core knows Unreal. Everything Unreal-side wraps it in
  `FAc*` and `UAc*` types and converts with `AcSpace.h`.

### 3.3 Instance budget

A late two-player game has about 400 units; eight players with big armies
could reach 1,500-2,000. At about 40 parts per unit (the Swift draw count
before flattening), that is 60-80k instance transforms a frame.

- Only moving parts need updating every frame. Static sub-assemblies follow
  the root: export them merged (the flattening already does this; the
  manifest says which parts have drivers).
- Parts with no driver can move with the root in a **single** transform per
  unit if the export merges them into one "body" mesh per material. Aim for
  5-15 moving parts per unit, not 40.
- Units out of the view frustum still need their transforms (shadows), but a
  unit off screen and outside the shadow box can skip its pose and keep its
  last one (`ac.PoseCull 1`).
- If CPU upload still dominates: per-instance custom data holding a walk
  phase, so the legs animate in the vertex shader (WPO about the pivot) and
  the CPU writes only the root. That is an optimisation for later (P2), not
  the first build.

### 3.4 Materials and team colour

- One master hull material with parameters: base colour texture or tint,
  roughness, metallic, normal, the team mask, and **custom data**: 0 team
  index (palette of 8), 1 emission scale, 2 alpha/fade (death sink, hologram
  pulse), 3 char (shatter ember amount).
- The emissive lamps are their own material (unlit, additive or opaque
  emissive), driven by custom data 1. The bloom threshold is set so they glow
  as in Swift (bloom 0.9, threshold 0.95).
- The painted skins (Prospector, Ranger, Comet, Juggernaut, Firefly) come
  baked into the export's textures. The team recolour needs a mask texture
  (the export agent: the blue-versus-red difference gives it).

### 3.6 Eight players

What changes in the game layer:

- **Colours.** A palette of 8 team colours (blue and red stay as 0 and 1),
  read from custom data. The minimap, scoreboard, hover tones, victory
  banner, beacons and life bars (enemy versus own) all key off the player
  index, never a blue/red bool. Today's code says `team`/`enemy` all over:
  in C++, write `owner == localPlayer` and `IsHostile(a, b)` (ask for
  alliances, question 1).
- **HUD.** The scoreboard becomes a list (army count per player, games won).
  The banner says the winner's name. Hover tips say whose a thing is.
- **Fog.** The renderer still shows one team's view. Eight players' vision
  costs the core, not the renderer.
- **Audio.** "Base under attack" is per local player only.
- **Cost.** The instance budget above, and the sim tick (§3.1).
- **Maps.** Bigger maps (the core's `WindowMaps`): the camera's minimum zoom
  and the minimap scale both follow the map size, as today.

### 3.7 The skeleton (A1): what every chunk builds on

Files in `Source/Autocraft/`; read the headers, they are the spec.

- **`AcSpace.h`** (namespace `AcSpace`, header only). **1 cell = 100 cm**
  (`CmPerCell`). `ToWorld(ac::Vec2, heightCells) → FVector(x·100, y·100,
  h·100)`, `ToSim(FVector) → Vec2`, `HeightToSim`, `ToCm`/`ToCells`.
  SceneKit `(x, y, z)` → `FromSceneKit` = UE `(x, z, y)·100`
  (`ToSceneKit` back); `AxesFromSceneKit` for directions and scales;
  `QuatFromSceneKit(x, y, z, w) = FQuat(-x, -z, -y, w)`;
  `TransformFromSceneKit(pos, quat, scale)`. Facing: **UE yaw = +heading
  in degrees** (`YawFromHeading`, `QuatFromHeading`, `RotatorFromHeading`;
  models face +X, buildings face UE +Y). Tests `Autocraft.Space.*`
  (round trips, yaw sign, 200 random SceneKit rotations) pass.
- **`UAcSimSubsystem`** (`AcSimSubsystem.h`, a `UTickableWorldSubsystem`,
  game and PIE worlds only; `UAcSimSubsystem::Get(this)`). Loads in
  `OnWorldBeginPlay`, so it is running before `AGameModeBase::StartPlay`.
  `Simulation()`, `State()`, `Map()`, `Session()`, `Choice()`,
  `LocalPlayer()` (0), `GameTime()`, `Shown()` (`sim.shown(0)`, once per
  frame on first ask), `Issue(ac::Command)` (its events join the next
  frame), `SetPaused`, `SetAI`, `NewGame(choice, teams)`, `Restart()`,
  `NextGame()` (called by itself after the 30 s victory lap), `Save()`
  (background, every 15 s and on quit; never for a `-AcSession` fixture).
  Each tick: dt clamped to 0.1, fixed 1/60 steps from an accumulator, then
  one `FAcFrame` (`State`, fog-gated `Events` as in
  `GameController.swift:318-335` with allies counted as own, `AllEvents`,
  `Time`, `Steps`, `RealDelta`, `Alpha`) to the listeners **in stage
  order**: `AddFrameListener(EAcFrameStage::Renderer|Effects|Audio|Hud|Other,
  FAcFrameEvent::FDelegate::CreateUObject(...))`. `OnGameStarted` fires
  when a game begins (load, new game, restart, next game): rebuild from
  `Map()` and `State()` there; if you subscribe late, check `IsRunning()`.
- **Command line.** `-AcSession=PATH` (JSON; relative paths from the repo
  root, e.g. `bench/badlands-large.json`), `-AcMap=badlands-large`
  (style-size[-players]: `highlands-small-8`; or the map's full name;
  resumes its saved game), `-AcNew`, `-AcTeams=4v4|2v2v2v2|0,0,1,1`,
  `-AcNoAI`, `-AcNoSave`, `-AcPaused`, `-AcRunFor=SECONDS` (headless:
  steps as fast as it can, logs a `simbench`-style line plus event counts,
  quits). Sessions live in `~/Library/Application Support/Autocraft/Unreal/sessions/`
  (the Swift game's stay apart).
- **`-AcShot=PATH`** (`AcShot.h`, `UAcShotSubsystem`): renders
  `-AcShotFrames=N` frames (default 60), saves the viewport as PNG, quits.
  `-AcShotUI` includes Slate. Code that must stage something first calls
  `UAcShotSubsystem::Get(this)->Hold()`/`Release()`; `OnBeforeShot` fires
  on the frame of the request. Needs a renderer (`-RenderOffscreen`, not
  `-nullrhi`).
- **`AAcGameMode`** (global default): `GetRunMode()` (Game, RunFor, Shot,
  Playground, Bench from the command line); no pawn yet (A3 sets it). Add
  your spawns in `StartPlay` or, better, in your own subsystem on
  `OnGameStarted`.
- **`LogAutocraft`** (`AcLog.h`). In `-game` runs it also goes to
  `~/Library/Logs/Autocraft/unreal.log` (Swift line format, with other
  categories' warnings and errors), not the Swift game's `autocraft.log`.
- **Map** `/Game/Maps/Battlefield`: an empty level, the game default.
  Everything in it is spawned from code.
- **Linking the core.** Unreal's Mac toolchain hides functions without an
  `_API` macro, so `AutocraftCore.Build.cs` force-includes
  `Module/AutocraftCoreVisibility.h` (`#pragma GCC visibility push(default)`)
  into the core's files. Windows would need a `.def` or export macros.

## 5. Risks

1. **Assets that are not text.** Materials, Niagara systems, input assets
   and imported meshes are binary `.uasset`s that agents cannot edit or
   merge (and three-way merges are this repo's rule). Every one must be made
   by a rerunnable Python script, and Niagara is the weakest part of the
   editor scripting API. Fallback: effects as C++-driven ISM sprite pools,
   with Niagara kept for the few systems that need it.
2. **Animation volume and per-frame cost.** About 15k lines of procedural
   pose code (GameScene, `Models+*`, the ModelViewer states, the cockpits)
   plus per-id renderer memory must be ported faithfully. Instancing then
   moves the bottleneck to tens of thousands of per-part transform uploads
   a frame. Reduce the moving parts at export first.
3. **Conventions and export fidelity.** Y-up right-handed to Z-up
   left-handed, the yaw sign, cm, pivots, and the exact terrain triangle
   split shared with the rays. The shader looks (opal, mercury, terrain
   splat, fog, sky, life bars, embers) exist only as notes in the manifest
   and must be rebuilt by hand.
4. **Mac specifics in UE 5.8.** Unknowns on Metal: VSM, Nanite, MegaLights,
   binaural HRTF, MP3 import (not supported), the user's music folder at
   runtime, media keys and Now Playing, trackpad gestures, and the M1 Air
   floor. Many lights at night with no MegaLights.
5. **UI that is far from stock.** The perspective-warped dashboard with
   inverse-mapped hit testing, the precise per-part crosshair (a shot
   between the legs misses), the camera clamp tied to the console height,
   and Slate written by hand for about 20 panels.

## 6. Open questions for the user

1. **Eight players.** Free-for-all, or teams (and if so, allies sharing
   vision, and colours by team or by player)? Is the human still one player
   (0) with seven AIs, or several humans (split screen, network)? This sets
   the hostility rules and the HUD.
2. **The floor and the look.** Is the floor still an M1 MacBook Air at
   30 fps (`Bench.speedup`), and is Windows a target now? That decides
   Lumen (planned off), Nanite, VSM and the light budget. Should the port
   match the SceneKit look first, or use UE's sky, volumetric fog and
   richer effects from the start?
3. **Generated binary assets.** Are `.uasset`s made by Python scripts and
   checked in (Git LFS?) acceptable, or should they be generated on each
   checkout and ignored?
4. **Wallpaper and screen-fitted maps.** Can the wallpaper and the maps
   fitted to the screens (Ashfall Reach, `MapView`) be dropped in Unreal, so
   it is window maps only?
5. **Font.** DIN Condensed is a macOS system font and cannot ship inside
   the game. Pick a shippable condensed font (Barlow Condensed, Oswald)?
6. **The user's music folder.** Keep dropping MP3s into a folder at runtime
   (this needs a decoder plugin, for example RuntimeAudioImporter), or ship
   only the soundtrack, imported?
7. **Saved games.** Should the Unreal game share `~/Library/Application
   Support/Autocraft/sessions/` with the Swift game (the same JSON), or keep
   its own?

### Answers (the user, 2026-10-05)

1. **Eight players: teams, one human (player 0) and seven AIs**, e.g. 4v4 or
   2v2v2v2. Allies share vision; colours per player.
2. **Target: the user's M4 Max only, at the best quality.** No floor Mac:
   Lumen, Nanite, virtual shadow maps and MegaLights are all allowed.
   Windows is not a target for now (keep the code portable anyway).
3. **The look: Unreal's richer look from the start** (sky atmosphere,
